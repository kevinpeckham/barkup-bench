# Study brief — Study AS: the PDF→template pipeline, measured (end-to-end fidelity benchmark of replicator's shipped reconstruction pipeline)

**Pre-registration, committed before any scored AS run.** Replicator
v3.269.0 ships the complete PDF→template pipeline: a user uploads a
PDF designed elsewhere, and the app reconstructs it as a native
template — decompose (vision → validated DesignSpec regions), match
(reuse org/system widgets vs build new), build (new widgets authored
under brand-compliance lint), assemble (pages + document template),
verify (render → block-similarity score → multimodal critic →
anchored-patch corrections with keep-best semantics). Every number
we have for it comes from TWO development E2Es on one real-world
PDF (final page scores 0.75/0.75, up from 0.53/0.34). Study AS
replaces that anecdote with a registered baseline: a 12-document
corpus of externally-designed PDFs across three difficulty tiers,
fixed gates, and per-stage diagnostics that say WHERE the remaining
error lives. This is the series' first whole-system study: the unit
under test is a shipped product pipeline, not an isolated protocol
variable — results feed replicator's roadmap, not a prompt decision.

## System under test

- replicator at v3.269.1 (commit `87f30a8` — the pipeline code is
  byte-identical to v3.269.0/`155036d`, which shipped Phase 3; 3.269.1
  adds only the harness's cleanup script), running as the dev VM's
  systemd service (`replicator-dev.service`, port 5183, same Turso
  DB and blob store as production). The exact commit running during
  scored cells is recorded in every raw record; if replicator moves
  mid-study, the run restarts.
- All five LLM stages run their shipped model,
  `anthropic/claude-fable-5.1` (PDF_DECOMPOSE_MODEL / PDF_MATCH_MODEL
  / PDF_WIDGET_BUILD_MODEL / PDF_CRITIQUE_MODEL / PDF_CORRECT_MODEL).
  No model matrix: AS measures the shipped configuration.
- Verify stage as shipped: similarity threshold 0.92, max 2
  correction iterations, keep-best (a correction that scores lower
  than the page's prior best is reverted).
- Org context: the preview-auth identity ("Screenshot Bot", admin of
  the SecureLogix org) — so the reuse catalog visible to the match
  stage is the SecureLogix org's widgets plus system widgets, a
  realistic mid-size catalog. The catalog is not mutated between
  items beyond the pipeline's own builds, and every created entity
  (template, pages, widgets, blobs) is deleted after the item is
  scored, so item order cannot grow the reuse pool. Cleanup is part
  of the harness contract and verified in the pilot.

## Corpus (committed alongside this brief, frozen by manifest)

12 HTML-designed documents in `corpus/pdf-pipeline/src/`, printed
to US-letter PDFs via headless Chromium
(`scripts/generate-pdf-pipeline-corpus.ts`) into
`corpus/pdf-pipeline/pdf/`, with sha256 hashes in
`corpus/pdf-pipeline/manifest.json`. The PDFs are the corpus — the
committed bytes are what every scored run ingests, checked against
the manifest hash before any scored call (Chromium version drift
can change regenerated bytes; the frozen PDFs make results
reproducible from the repo alone).

Disclosure: the corpus was authored by an LLM agent to a registered
item spec (12 named designs, fictional entities, self-contained
HTML, varied palettes/typography/density) — which matches the
product scenario under test ("a PDF designed by another user or
agent") but means corpus style is one generation away from the
model family being measured. Items were accepted on visual/validity
review BEFORE any pipeline run; no item may be edited, re-rendered,
or swapped after the first scored cell.

Tiers:

- **T1 simple (4 items, 1 page):** `t1-memo`, `t1-event-flyer`,
  `t1-press-release`, `t1-menu` — single-flow layouts.
- **T2 medium (4 items, 1 page):** `t2-product-sheet`,
  `t2-stat-onepager`, `t2-newsletter`, `t2-agenda` — multi-region
  compositions (column splits, tile grids, rails).
- **T3 hard (4 items, 2 pages):** `t3-annual-report`,
  `t3-case-study`, `t3-brochure`, `t3-prospectus` — dense mixed
  layouts, 2 pages each.

16 scored pages total (T1 4 + T2 4 + T3 8).

## Protocol

One arm. For each corpus item, the runner
(`src/harness/pdf-pipeline-runner.ts`) drives the shipped stage
endpoint (`POST /api/pdf-template-pipeline`) exactly as the product
client does: `start` (upload PDF bytes) → `decompose` per page →
`match` per page → `build` per region marked build → `assemble` →
`verify` per page, threading the validated state blob between
requests. Auth = `x-preview-token` header + `activeOrg` cookie (the
shipped preview bypass). After scoring, the runner deletes the
created template, pages, widgets, and their blobs, and the raw
record keeps the full final state blob, per-stage wall-clock, and
every stage's response.

Items run sequentially in a fixed registered order (t1-memo …
t3-prospectus, the manifest order). One run through the corpus; a
hard transport failure (network/5xx unrelated to the pipeline's own
validation) may be retried once per stage, recorded; a pipeline
error (stage returns a structured failure) is a completion failure
for that item, not retried.

**Pilot gate (harness validation, not a spend gate — spend was
approved 2026-10-21):** `t1-event-flyer` + `t3-case-study` run
first. STOP after these two: verify raw records are complete,
cleanup left zero rows/blobs, and per-item cost/latency is in the
expected band, then proceed to the remaining 10 with the harness
untouched. Any harness fix after the pilot restarts the full corpus
(pilot cells are re-run; nothing from a broken harness is kept).

## Measures

Primary, per scored page (from the pipeline's own verify stage,
whose block-similarity scorer is unit-tested in replicator):

- `initialScore`, `finalScore` ∈ [0,1] — 16px block-diff similarity
  between the rendered reconstruction and the source page PNG.
- verify `iterations`, `findingsApplied`, `reverted`.

Per item: completion (all stages succeed), region count, reuse vs
build decision split, fallback-widget count, per-stage wall-clock.

Descriptive only (disclosed limitation): token/dollar cost is not
instrumented per stage in the shipped pipeline; the study reports
wall-clock and a corpus-level spend estimate from the gateway
dashboard, not per-cell cost.

## Registered gates

- **G1 completion:** ≥ 11 of 12 items complete every stage without
  a pipeline error.
- **G2 fidelity:** median `finalScore` across all scored pages
  ≥ 0.70, AND T1-tier median `finalScore` ≥ 0.80.
- **G3 refinement:** (a) keep-best invariant holds on every page
  (`finalScore ≥ initialScore`, no exceptions — a single violation
  fails the gate and is a replicator bug); (b) among pages that
  enter correction (`initialScore < 0.92`), median uplift
  (`finalScore − initialScore`) ≥ +0.05.
- **G4 build integrity:** fallback widgets ≤ 10% of built widgets
  across the corpus.

Gates are a BASELINE registration: pass/fail says whether the
shipped pipeline holds its development numbers on foreign designs.
A failed gate is published as measured (the series' standing rule)
and names the stage to improve; it does not trigger un-shipping.

Secondary questions (descriptive, no gates): where does residual
error concentrate (initial-score deficit by tier = decompose/build
quality; uplift exhausted at max iterations = verify ceiling);
does reuse rate differ by tier; do 2-page items degrade on page 2.

## Spend

~12 items × 1–4 pages × (decompose + match + builds + ≤2 critic/
correct rounds) on fable-5.1 ≈ $15–40 total, inside the approved
envelope. Abort and report if the pilot projects > $80.
